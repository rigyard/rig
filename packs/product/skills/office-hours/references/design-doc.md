# Phase 5: design doc, and Phase 6: handoff

## Phase 5: Design doc

Write the design doc into the user's repository, at `docs/designs/<slug>.md` under the repository root (`git rev-parse --show-toplevel`). `<slug>` is a short topic name in lower-case kebab case, for example `sound-recorder-beats`.

**Lineage.** Never overwrite an existing design doc. If `docs/designs/<slug>.md` exists, use the next free `<slug>-2`, `<slug>-3`, and so on. If the new doc revises a prior one (an existing doc with this topic, or the related design that the user chose to build on in Phase 2.5), add a `Supersedes:` line that names the prior path. This keeps a revision chain: you can trace how a design changed across sessions.

**Check before you write.** The doc is meant to be committed and shared. Before you write it, read the exact text for secrets and private data: tokens, keys, credentials, private contact details. Remove each one, or ask the user how to handle it.

**Fallback.** If the directory is not a git repository, the checkout is read-only, or the write fails, say why in one line, print the full doc inline, and ask the user where to save it. The handoff continues either way.

**Decision-record concision.** The doc is a decision record, not a transcript. Write one bullet per decision with its reason. An approach the user ruled out during the session gets one line (name and rejection reason), never a full section that argues the case again. Omit template sections that are empty or that restate what is already settled. There is no page cap, but extra length must come from open questions, not from filling the template.

After you write it, tell the user: "Design doc saved to: docs/designs/<slug>.md."

### Review and approval

1. **Show the whole doc.** Print the complete doc as text in your own message: "Here is the design doc saved to docs/designs/<slug>.md. Please review it before you approve:", then the verbatim body. Do not ask the user to open the file, and do not rely on a tool call's output to show it. Tool output is often collapsed, and the user would approve a doc they cannot see.
2. **Approval.** Ask:
   - A) Approve: set `Status: APPROVED` and go to the handoff
   - B) Revise: name the sections to change (loop back and revise them)
   - C) Start over: return to Phase 2

## Phase 6: Handoff

Start this phase only when the doc is APPROVED.

### Signal reflection

Write one paragraph that reflects the founder signals from Phase 4.5 back to the user. Name the signals you counted and when each one showed up. Reference specific things the user said, and quote their words.

Show, don't tell:

- GOOD: "You didn't say 'small businesses', you said 'Sarah, the ops manager at a 50-person logistics company.' That specificity is rare."
- BAD: "You showed great specificity in identifying your target user."
- GOOD: "You pushed back when I challenged premise #2. Most people just agree."
- BAD: "You demonstrated conviction and independent thinking."

Then restate the assignment from the doc in one line.

### Next step

End with the design doc path, `docs/designs/<slug>.md`, with the final slug.

Do not start the build yourself. The hard gate holds until the skill ends: the user runs the next command.
