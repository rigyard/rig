# Prior art: skill managers, distros, slots and testing

Status: research record, 2026-11-04. Star counts and repository facts come from the GitHub API on that date. A research summary without a recorded URL says "URL not recorded".

## Summary

- No existing tool covers what rig needs: pinned copies, a fixed core, slots with one provider, a gate before every write, and targets for Claude Code, Codex, omp, pi and Hermes.
- Microsoft APM is the closest match. [Decision 0014](../decisions/0014-build-rig-borrow-from-apm.md) (Proposed) borrows its lockfile with content hashes, its hidden-Unicode audit and its tighten-only policy model.
- No harness and not the Agent Skills specification has a native slot concept. rig must implement slots at render time.
- Non-agent distros (Debian, Nix, Doom Emacs, LazyVim, ESLint, VS Code) give eight rules that transfer.

### What works

- One source, generated per harness, with the output committed.
- The SKILL.md folder as the unit of distribution.
- Git catalogs pinned by ref or SHA.
- Profile or preset layers.

### What fails

- Drift and overwrites without a message.
- Breaking upgrades of the configuration format (BMAD version 7, agent-os version 3).
- Name collisions that the tool resolves without a message.
- Context cost from too many listed skills.
- Supply chain. A Snyk audit of 3,984 skills in February 2026 found 36.8% with flaws and 76 malicious (secondary source, unverified).
- Experimental or weak lockfiles.

## Non-agent distros: the eight transferable rules

Prior art: Debian alternatives, VS Code `defaultFormatter`, Nix modules, Doom Emacs, LazyVim, ESLint flat config. Source: research summary R2, 2026-11-04, URLs not recorded.

1. A slot is exclusive. One provider is active. The distro declares a default and the user picks by name (Debian alternatives, VS Code `defaultFormatter`).
2. Keep automatic and manual choice apart, so an upgrade does not override a user pick.
3. Two providers for one slot is a loud error. No numeric priorities. Two levels only: distro default and user choice. Nix raises a duplicate-definition error. Nix priorities are the part that users find hard.
4. A lockfile per install pins every provider. An upgrade shows an explicit diff that you review (Doom `sync` and `upgrade`, LazyVim lock).
5. Override by name in a user layer. Do not edit the core (LazyVim `import`, Doom `$DOOMDIR`).
6. Small core, opt-in modules, cheap defaults. Context cost is the agent equivalent of startup time.
7. Each module declares its dependencies (ESLint flat config).
8. Version the configuration schema from the first release. Ship a migration shim when a change breaks it (ESLint `FlatCompat`).

## Native slot support per harness

Result: none. No harness and not the Agent Skills specification has "provides X", "a slot with one provider" or "depends on whatever fills X". Source: research summary R3, 2026-11-04.

| Surface | Nearest feature | Gap |
|---|---|---|
| Agent Skills specification | `metadata`, a string map | The only safe place for rig keys such as `rig-slot` and `rig-provider`. |
| Claude Code | Plugin `dependencies` by plugin name. Plugin skills have the namespace `plugin:skill`. `skillOverrides` by name, not for plugin skills. `${user_config.KEY}` substitution in plugin skills. | No slot. Substitution for slots is untested. |
| Codex | `[[skills.config]]` disables by path or name. | Same-name skills are not merged. Both show. |
| omp | The loser of a name collision gets the name `<ns>/<name>`. `manualSkills`, `ignoredSkills`. | No slot. |
| pi | The first same-name skill wins, with a warning. | No slot. |
| Hermes | `fallback_for_tools`, `fallback_for_toolsets`, `requires_*`. | Visibility depends on tools, not on skills. |

Consequence for rig: rig renders one stable stub skill per slot, for example `rig-doc-review`. The body holds the active provider's instructions, a delegation line to the provider's entry command, or one line that says the slot is empty or the provider is not available on this harness. Core skills name the slot by stub name in prose. They never name a provider or a path. Native hide and disable settings only hide providers that are not in use.

## Google Harness²

`google-research/harness2` (https://github.com/google-research/harness2). Sources are secondary only (unverified).

- A research framework. It optimizes the harness around a frozen model with designer and editor agents.
- Benchmarks: LAB, JobBench, WorkBuddy. It drives OpenCode and Codex only. It uses about 4,000 agent calls per task.
- Version 0.1.0, Apache-2.0, "not an officially supported Google product".
- It is not a skill-testing tool, so it is out of scope for v0.
- Its loop is useful later. An agent proposes a rule change, runs a task set and keeps the change if the score improves. rig can add a `rig hillclimb` command on top of promptfoo or agent-skill-eval when rig has its own task set.

| Harbor, Terminal-Bench | General agent ability. | Not for skills. |

Source: research summary R3 (wave 2), 2026-11-04.

Recommendation for v0: an in-house smoke test per harness. Run the harness headless with a prompt that forces the skill. Assert that the transcript shows a read of the installed SKILL.md. Behavioral evals wait for a promptfoo or agent-skill-eval spike on one skill.
